# 02 · 私域 / 公域与客户归属机制详细设计（防撬客核心）

> 这是全案信任地基。目标：智能撮合只动公域无主流量，商家老客户（尤其高价值）绝不被推给竞争对手。本章给出归属判定规则引擎、状态机、保护期与撞单仲裁的完整逻辑。

---

## 1. 概念定义

| 概念 | 定义 |
|---|---|
| 私域客户 | 已与某商家建立归属关系的客户，平台不向第三方分发其需求 |
| 公域流量 | 未与任何商家建立归属、或客户自愿公开的需求，可参与智能撮合 |
| 归属关系 | `customer_relation` 记录，连接商家与客户企业 |
| 保护期 | 归属关系受保护的时间窗口，期内独占/优先 |
| 战略客户 | 商家标记的高价值客户，永久绑定、永不入公海 |

---

## 2. 归属判定规则（建立私域）

客户满足任一条件即在该商家名下创建/激活 `customer_relation`：

| 触发方式 | relation_type | 初始保护期 |
|---|---|---|
| 商家导入通讯录/客户表 | imported | 短（如 30 天，需后续互动续期） |
| 商家邀请注册（专属邀请码/链接） | invited | 中（如 60 天） |
| 发生询价/报价/看货 | dealt(pre) | 中（如 60 天） |
| 完成成交/回款 | dealt | 长（如 90 天） |
| 商家主动认领公海客户 | claimed | 中（如 60 天） |
| 标记为战略客户 | 任意 + is_strategic | 永久 |

> 保护期数值为可配置参数，建议平台统一默认值并允许按商家等级调整。

---

## 3. 归属状态机

```
            导入/邀请/询报价/成交/认领
   (无归属) ───────────────────────────▶ active(私域, 保护期内)
                                              │
        保护期内发生有效互动 ◀────────────────┤ 自动续期
                                              │
                              保护期到期且无新互动
                                              ▼
                                       expired(私域,宽限期)
                                              │
                          宽限期内仍无互动      │  宽限期内恢复互动
                                              ▼          ▲
                                    returned_to_pool ─────┘(重新认领→active)
                                       (回到公域)

   战略客户：靠"经营时钟"维持；持续经营=永久保护，长期不经营→降级(非直接入公海)
```

- **active**：保护期内，需求独占/优先归该商家。
- **expired**：保护期到期但尚在"宽限期"，仍属私域、仅降低优先级提醒商家"客户快流失"。
- **returned_to_pool**：宽限期后仍无互动 → 回公域，可被其他商家认领。
- **战略客户**：无固定保护期，靠"经营时钟"(`last_interaction_at`)维持；只要持续经营即**永久保护、永不入公海**；长期完全不经营会被**降级为普通保护**（详见第 11 节反囤积治理）。

### 3.1 保护状态参数（可配置，默认值示意）

| 参数 | 默认 | 含义 |
|---|---|---|
| 保护期(imported) | 30 天 | 导入客户基础保护期 |
| 保护期(invited/inquired/claimed) | 60 天 | 邀请/询价/认领 |
| 保护期(dealt) | 90 天 | 有真实成交 |
| 宽限期 GRACE_DAYS | 30 天 | active 到期后仍属私域的缓冲 |
| 战略待复核 STRATEGIC_REVIEW_DAYS | 180 天 | 战略客户超此无互动 → 告警"待复核" |
| 战略降级 STRATEGIC_GRACE_DAYS | 365 天 | 战略客户超此无互动 → 自动降级为普通保护 |

> 普通客户"保护是挣来的"：靠真实互动续期；不经营则 active→expired→公海。
> 战略客户"高门槛、低频维持"：极长宽限 + 极低维持频率即可永久保留，但**非永久免检**。

## 4. 有效互动与自动续期

**有效互动定义**（任一发生即刷新 `protect_until`）：
- 新的询价/报价往来；
- 新的看货/到访；
- 新的成交或回款；
- 商家主动跟进并被客户回应（双向沟通，非单方群发）。

续期逻辑：
```
on 有效互动(merchant, customer):
    rel = get_relation(merchant, customer)
    rel.protect_until = max(rel.protect_until, now + base_period(rel.relation_type))
    if rel.status == expired: rel.status = active
```

> 单方群发**不算**有效互动，防止商家"刷消息"长期霸占客户却不真正服务。

---

## 5. 撞单仲裁（多商家争同一客户）

当一个客户与多个商家存在关系时，按优先级链判定"该需求归谁/谁可优先报价"：

**仲裁优先级（从高到低）：**
1. **战略锁定**：被某商家标记为战略客户 → 独占该商家（互斥，平台限制同一客户只能被一家设为战略，先到先得 + 客户可申诉）。
2. **保护期 + 成交关系**：active 且 relation_type=dealt（有真实成交）。
3. **保护期 + 询报价关系**：active 且 dealt(pre)。
4. **保护期 + 邀请/导入**：active 且 invited/imported。
5. **谁先建立关系**：同档位按 created_at 早者优先。
6. 均无归属 → 进入公域撮合。

**输出**：仲裁结果决定该 demand 的"分发范围"：
- 命中私域归属 → 仅通知归属商家（独占报价权或保护期内优先报价权）。
- 无私域归属 → 进公域池，按撮合算法分发给若干匹配卖方（详见 03 章）。

---

## 6. 可见性模型（商家自控）

每个 `customer_relation` / `listing` 带 `visibility`：

| 取值 | 含义 | 默认适用 |
|---|---|---|
| private | 仅归属商家可见，绝不撮合 | 战略/高价值客户默认 |
| assigned | 仅推给商家指定的对象 | 商家定向合作 |
| public | 进入公域，参与撮合换流量 | 无主新客/客户自愿公开 |

商家可对每个客户/货源单独设置，选择权完全在商家手里。

---

## 7. 公域 ↔ 私域流转规则

- **公域 → 私域**：商家认领公海客户、或与公域需求成交 → 自动建立归属。
- **私域 → 公域**：仅在 `returned_to_pool`（长期不服务）或商家主动退回时发生；**战略客户永不流转**。
- **冲突保护**：客户回公域后被新商家认领时，对原商家发"客户已流失提醒"，并保留可申诉/挽回入口。

---

## 8. 规则引擎设计

- **形态**：可配置规则引擎（参数化保护期、宽限期、有效互动定义、仲裁优先级），便于运营按行业反馈调参，不用改代码。
- **执行时机**：
  - 实时：询报价/成交/认领发生时即时判定归属与续期。
  - 定时：每日扫描 `protect_until`，处理 active→expired→returned_to_pool 流转，并触发提醒。
- **幂等与审计**：每次归属变更写入审计日志（详见 06 章），可追溯"谁在何时因何规则获得/失去某客户"。

---

## 9. 关键接口（草图）

- `POST /relation/claim` → 认领公海客户
- `POST /relation/strategic` → 标记/取消战略客户
- `PUT /relation/{id}/visibility` → 设置可见性
- `GET /arbitration?demand_id=` → 查询某需求的归属仲裁结果
- `GET /relation/expiring?merchant_id=` → 即将掉保的客户（供运营提醒）

## 10. 与商家的契约表达（产品文案层）

把规则翻译成商家能秒懂的承诺，写进产品界面与平台公约：

- 「**你的老客户永远是你的**，只要你在经营，平台就一直为你保护。」
- 「高价值客户可设为**战略客户**：持续经营下永不进公海、永不被撮合。」
- 「客户联系方式由平台**加密托管**，同行拿不到。」
- 「你能随时查看**客户被谁看过、有没有被分发**的记录。」

## 11. 战略客户反囤积治理（核心生态设计）

### 11.1 问题：商家一定会"把所有客户都圈成战略客户"

如果"战略锁定"是免费、无限、永久免检的，那么**每个理性商家都会把全部私域客户一次性锁死**。后果：
- **公海枯竭**：没有无主流量可供撮合，平台失去网络效应，退化成一堆互相封闭的 CRM。
- **客户被劫持**：客户被一个**不再服务他**的商家长期锁死，损害客户体验，也违背"保护关系而非圈地"的初衷。
- **数据底座失真**：商家把一切都标成战略以求"绝对安全"，分层与撮合都失去意义。

所以战略保护必须是**稀缺的、有成本的、需经营维持的、且客户可制衡的**——"保护是挣来的，不是圈来的"。

### 11.2 四道治理闸门

**① 价值准入 + 动态容量 —— 防"全量圈地"，且大小商家都合理**

固定数字配额（如统一 20）不合理：大商家不够、小商家太多。改为**价值导向 + 自动伸缩**：

- **价值准入门槛**：只有客户对该商家的**价值分**达标才有资格设为战略客户。价值分由"近 12 月成交额（毛利代理）+ 复购频次 + 最近活跃 + 合作时长 + 回款表现"加权（实现见 `value.py::customer_value_score`，0-100，门槛默认 40）。低价值客户被 `NotEligibleStrategic` 拒绝。
- **动态容量**：上限随商家规模自动伸缩，`容量 = clamp(基础值5, ⌈活跃客户数 × 10%⌉, 硬上限)`，并可按付费档封顶（`set_strategic_quota` 覆盖）。大商家自然多、小商家自然少。
- **价值持续性**：战略身份不仅要"经营时钟"有互动，价值跌破门槛也会进入待复核→降级。
- 把"战略保护"变成**靠价值挣来的稀缺资源**，而非随意圈地。

> 冷启动期 `value_gate=False`（仅动态容量生效，规则保底）；交易数据充足后开启价值门槛——契合"先规则后模型"。

**② 经营时钟（Use-it-or-lose-it）—— 防"圈而不耕"**
- 战略客户无固定保护期，但维护一个"经营时钟"`last_interaction_at`，每次真实双向互动刷新。
- 超过 `STRATEGIC_REVIEW_DAYS`(默认180天)无真实互动 → 标记**待复核(at_risk)**，看板告警提醒商家。
- 超过 `STRATEGIC_GRACE_DAYS`(默认365天)无真实互动 → **自动降级为普通保护客户**。
- **关键**：降级是"战略 → 普通保护(仍 private)"，**不是直接入公海**——给商家充分缓冲与告警，守住"永不入公海"的信任承诺；只有降级后再长期不经营，才会按普通规则最终回公海。
- 单方群发不算互动，防"刷消息续命"。

**③ 客户制衡（Customer Agency）—— 最终兜底**
- 客户不是商品。客户可查看"哪些商家把我列为重点保护"，并有权**主动解除绑定**(`customer_opt_out`)。
- 客户主动解除 → 关系直接回公海，可被重新撮合/认领。
- 这是防止不合理锁定的最根本制衡：**保护的是关系，而关系需要双方认可**。

**④ 平台调控（可选）—— 生态健康**
- 监控公海流动性与各商家"私域占比/服务质量"；对异常囤积且服务质量低者，可调低其名额或触发治理。

### 11.3 状态流转（含战略治理）

```
            mark_strategic (占用名额, 全局互斥)
   普通保护 ──────────────────────────▶ 战略(private, 经营时钟)
       ▲                                    │
       │ 降级(仍 private,给普通保护期)        │ 持续真实互动 → 永久保留
       │ ◀──────────────────────────────────┤
       │        超 365 天无互动 / 商家主动释放 │
       │                                    │ 客户主动解除
       │                                    ▼
   普通规则掉保流转                      returned_to_pool(公海)
```

### 11.4 接口（草图）
- `POST /relations/strategic` → 设战略客户（价值不达标或容量满返回 403）
- `GET /strategic/eligibility/{customer_id}` → 资格评估（价值分/已用/容量/原因）
- `DELETE /relations/strategic/{customer_id}` → 释放名额（降级为普通保护）
- `GET /strategic/quota` → 容量使用情况 + 待复核(at_risk)战略客户
- `POST /relations/customer-opt-out` → 客户侧主动解绑（回公海）

> 实现见 `prototype/steel_platform/value.py`（价值分/动态容量）与 `ownership.py`：`strategic_eligibility / strategic_capacity / strategic_health / unmark_strategic / customer_opt_out / refresh_states(降级)`，配套单元测试覆盖价值门槛、动态容量、降级、客户解绑。

## 12. 买方寻源自由 vs 卖家关系保护（Push / Pull 平衡）

### 12.1 关键澄清：保护的是"卖家关系"，不是"囚禁买方"

战略/私域保护**绝不等于**"买方被某卖家独占、不许找别人"。量大的买方天然要多找供应商比价，买方也有自主采购权；若平台禁止买方向他家询价，买方会问"我为什么要用这个平台？"——这会摧毁平台对买方的价值，也涉嫌不正当限制。

因此把需求分成两条通道，区别对待：

| 通道 | 含义 | 规则 |
|---|---|---|
| **平台 Push（被动分发）** | 撮合引擎主动把需求推给卖家 | 买方有私域归属 → **不进 Push 池**，平台绝不替卖家把客户当流量分给同行（这才是"防撬客"真正要拦的） |
| **买方 Pull（主动公开寻源）** | 买方自己发起公开询价/招标/比价（`is_public=true`） | **永远自由**：即便买方是某商家的私域/战略客户，也可向任意卖家询价；但**归属商家(老关系)享优先响应权** |

### 12.2 老关系的"优先响应权"（而非"独占权"）

当战略/私域买方主动公开寻源时：
- 系统**允许**其他公域卖家参与报价（尊重买方自由）；
- 但**归属商家**的货源被标记 `priority` 并**排序靠前**（优先响应/优先展示），可叠加"优先报价窗口"（老关系先报 X 分钟，或买方选择"多家比价"后才放开）。

这样：
- 买方不会被绑死 → 留在平台有意义（能高效比价、能找到更多货源）；
- 卖家老关系仍有**实质优势**（优先权）且平台不主动撬 → 卖家愿意把真实客户放进来；
- "保护"从"独占垄断"修正为"优先服务"，更可持续、更公平。

### 12.3 实现
- `matching.py::_is_eligible_demand`：私域买方的**非公开**需求不进撮合（防 Push 撬客）；**公开**需求放行（买方 Pull 自由）。
- `matching.py::match_for_demand`：公开需求且买方有归属时，归属商家货源 `priority=True` 且排序最前。
- `ownership.py::active_owner_merchant`：返回买方当前归属商家，用于授予优先权。
- 测试见 `test_value_and_freedom.py::TestBuyerSourcingFreedom`（被动需求不被 push；公开寻源可达他家且老关系优先）。
